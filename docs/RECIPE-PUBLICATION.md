# Recipe publication

`gates provenance publish <registry> <repo> <sourcePath> <ref> [<version>] [--kind <kind>]` refuses a source path with uncommitted changes, takes the last commit touching the path as `defRef`, and writes `registry/recipe/<ref>/<version>/recipe-setpoints.yaml` (the file bytes from that commit) and `manifest.json` (`kind`, `ref`, `version`, `defRef`, `contentSha256`, `sourcePath`, `publishedAt`). Versions are immutable. Unsigned publish keeps working as before. Muninn and resequence-twin-lab read `manifest.json` by path. `gates provenance verify <registry> <ref>` recomputes the SHA-256 of the canonical file of the highest version and compares it with `contentSha256`.

## Publisher attestation

With `--by <principal> --by-key <keyFile>` (the two flags go together) the publisher also writes `manifest.dsse.json` in the same directory: a DSSE v1.0.2 envelope (`payloadType` `application/vnd.in-toto+json`) holding an in-toto Statement v1 whose `predicateType` is `https://slsa.dev/provenance/v1`. One Ed25519 signature is generated by the publisher over PAE(payloadType, payload); `keyid` names the principal and is only a hint. The statement claims that this principal published these two files, generated from this git commit. It does not claim a review: review happens in git, and two-person approval happens at activation. No SLSA build level is claimed.

Before anything is written, the key file must match a key registered for the principal in `identity/authorized-keys.jsonl` and be inside its validity window, and `identity/activation-policy.json` must grant the principal `publish` on target `recipe-publication`, with `kind` equal to the manifest's `kind` (default `recipe-setpoints`) and the `ref`. A refused publish writes nothing and exits 1. The envelope is written first (a `.pending` file moved into place), then the canonical file, then `manifest.json`. A process stopped in between leaves an envelope with no manifest; a signed retry replaces it. `manifest.json` is byte-identical to an unsigned publish.

A signed publish of a version that already exists keeps its valid envelope unchanged, refuses an envelope that does not verify, and refuses `recipe.publish.already-published-unsigned` when the version was published without one. A version is never signed after the fact.

## Build type v1

Statement `subject` has two entries, `recipe-setpoints.yaml` and `manifest.json`, each with `digest.sha256` over raw file bytes; the seven manifest fields are bound through the manifest digest. Predicate fields:
- `buildDefinition.buildType`: `https://github.com/yggdrasil-iiot/bifrost/blob/main/docs/RECIPE-PUBLICATION.md#build-type-v1`.
- `buildDefinition.externalParameters`: `kind`, `ref`, `version`, `sourcePath`, `publishedBy`.
- `buildDefinition.resolvedDependencies`: One entry, `name` = `sourcePath`, `digest.gitCommit` = `defRef`.
- `runDetails.builder.id`: `https://github.com/yggdrasil-iiot/bifrost/gates/provenance-publish`.
- `runDetails.metadata.finishedOn`: `publishedAt` in UTC to the second (the manifest keeps the milliseconds).

## Verification

1. Decode the payload without Bifrost code.
2. Take `publishedBy` and verify the signature over PAE with that principal's registered key.
3. Check `_type` and `predicateType`.
4. Check that the subject digests equal the raw SHA-256 of the two files.
5. Check that `externalParameters` and `resolvedDependencies` restate `manifest.json`.

`gates provenance verify-attestation <registry> <ref> <version>` exits 0 when the envelope verifies and 1 with a reason code otherwise; an unsigned version is refused (`recipe.attestation-missing`), never accepted on the SHA-256 check alone. It checks, in order: the publisher named in `publishedBy` signed with a registered key; `_type`, `predicateType`, `buildType` and `builder.id`; the subject equals the two files on disk; the predicate restates `manifest.json` and the requested ref and version; the policy still grants that publisher `publish`. Reason codes: `recipe.attestation-missing`, `recipe.attestation-signature:<identity rule>`, `recipe.attestation-statement`, `recipe.attestation-subject`, `recipe.attestation-subject:line-endings`, `recipe.attestation-predicate`, `recipe.publish-denied`. The `publish` grant is Bifrost policy and is not part of the statement. A key retired later still verifies what it signed; the validity window is checked when signing. The activation ledger seals `spec/<ref>/<version>.json`, a different file; the publisher attestation covers the recipe registry and does not link the two.

## Registry bytes

Bifrost seals raw file bytes in two places: the publisher attestation subject (`recipe-setpoints.yaml` and `manifest.json` under `recipe/<ref>/<version>/`) and the activation ledger (`spec/<ref>/<version>.json`, which Heimdall hashes again before it binds the version). Bifrost writes `manifest.json` with LF line endings on every OS and copies `recipe-setpoints.yaml` byte for byte from the git commit.

A copy that converts line endings changes those bytes. Git with `core.autocrlf` does this on checkout and on commit. The result is refused like any other changed byte. The refusal names the cause when the only difference from the sealed bytes is line endings: `gates provenance verify-attestation` refuses with `recipe.attestation-subject:line-endings`, and Heimdall fails with `activation.edge.content-mismatch:line-endings`. The fix is to restore the original bytes, not to re-seal.

Keep a registry that lives in git out of line-ending conversion with a `.gitattributes` file at the root of that repository containing exactly these two lines:

```gitattributes
recipe/** -text
spec/** -text
```

Files already converted by an earlier checkout come back once the attributes are committed: delete the converted copies and run `git checkout -- recipe spec`, which writes the bytes git stores.
